# First-class tour narration with text to speech

## Status

Proposed as an independently shippable accessibility and usability feature.
It does not depend on microphone input, conversational voice, or an agent
connection.

## Goal

Let a reader listen to an authored or generated Bygone tour while the
presenter advances through the same scenes, steps, files, and anchors shown on
screen.

The release bar is not merely that speech comes out of the speakers. The
default supported experience must be natural and intelligible for sustained
technical narration, recover cleanly from navigation and interruption, and
remain useful without requiring the reader to watch every control.

## Why this stands alone

The compiled tour already contains ordered narrative text and stable scene and
step identities. Speaking that text is a bounded presentation concern. It
does not require speech recognition, an LLM, repository write access, or a
route back to the authoring agent.

This separation matters because good read-aloud support is valuable on its
own for readers with low vision, dyslexia, fatigue, repetitive-strain limits,
or a preference for listening while following code. It should not wait for a
much larger conversational system.

## User experience contract

### Entry points

Add a compact narration group to the tour narrative header:

- **Listen** starts at the active scene or step;
- **Pause/Resume** preserves the current narration unit and playback intent;
- a voice/rate menu exposes only settings the active speech engine supports.

The existing **Previous** and **Next** controls continue to own linear tour
navigation and gain the playback behavior described below; do not add a second
pair of navigation buttons.

The first release should also provide a **Listen to Tour** action in the
Present menu and keyboard-accessible controls in both the Electron window and
browser presenter. Playback never starts automatically when a tour opens.

Every control needs a stable accessible name, visible focus, useful disabled
state, and a status announcement such as “Playing step 2 of 4” or “Narration
paused.” Device TTS is the default and works without a network connection. An
offline state must not disable narration during normal operation. If the host
exposes no usable device voice at all, disable Listen with specific setup or
platform-support copy rather than reporting a generic network failure. Do not
use sound alone to communicate playback state or errors.

### What is spoken

Build speech from the semantic tour model rather than scraping rendered DOM
text. A narration unit contains:

1. chapter and scene title when entering a scene;
2. scene summary and bullets;
3. the current step title and body, including a connection label when present;
   and
4. the scene takeaway after its final step.

Tags, commit hashes, line numbers, diff statistics, and source code are not
spoken by default. File paths may be announced as short orientation cues, but
the engine must not attempt to read punctuation-heavy code or full object IDs
unless a later explicit “read selection” feature is designed.

Every automatically spoken segment must correspond to text visible in the
presenter. Treat technical content as follows:

| Visible content | Spoken treatment |
| --- | --- |
| Narrative prose | Speak the authored words with conservative pronunciation normalization. |
| Scene/step titles and bullet items | Speak as their own segments. |
| Inline identifiers in prose | Speak them as prose; normalize demonstrated cases such as camel-case boundaries or common initialisms without changing the visible text. |
| File paths used for orientation | Speak a short, humanized label, normally the basename and file type; keep the full path visible. |
| Links in narrative UI | Speak the visible link label only, never the raw URL, scheme, query string, or tracking parameters. |
| `sourceUrl`, commit links, and navigation controls | Do not include them in automatic narration. |
| Code blocks, diff lines, hashes, line numbers, and raw URLs | Do not speak them automatically. |

The version-1 tour narrative is plain text rather than rich Markdown, so the
first release does not add code/link annotations or speech markup to the
authoring format. Special treatment is a speech-only projection of content the
presenter already knows semantically.

Starting from the middle of a tour should give enough context to orient the
reader without replaying the entire scene. Starting on a stepped scene speaks
the scene title, then the active step. Continuous playback speaks the scene
introduction once, each step once, and the takeaway once.

### Spoken highlighting and granularity

Split each narration unit into deterministic speech segments before sending it
to the engine. A segment is normally one sentence. A title, bullet item, short
step body, connection label, or takeaway may be a single segment even when it
has no terminal punctuation. Use 240 characters as the initial segment ceiling
and split an unusually long sentence at the nearest natural clause boundary.
This keeps the usual highlighted interval to one sentence and prevents the
reader from waiting through a large paragraph before the highlight or controls
respond. Tune that ceiling only from listening and interruption tests, not as a
new user preference.

Highlight exactly the active segment in the visible narrative while it is
spoken. The highlight follows sentence-sized segments, not individual words:

- use a distinct background/border treatment that does not rely on color
  alone and does not replace the browser or screen-reader selection;
- scroll the segment into view only when it has left the narrative viewport;
- keep keyboard focus where the reader put it;
- retain the active highlight with a paused treatment on pause, then clear it
  on stop, navigation away, error, or completion; and
- expose the full original sentence to assistive technology without causing
  it to be announced again on every visual highlight change.

Drive playback one segment at a time so highlighting and interruption do not
depend on vendor-specific word-boundary timing. Word-by-word karaoke,
phoneme-level timing, and highlighting source-code tokens are not part of the
first release.

### Synchronization and interruption

Narration follows the existing linear tour order. When one unit completes,
the presenter advances the visible scene or step before the next unit begins.
The active file, diff, focus marker, and breadcrumb therefore remain aligned
with the speech.

- Pausing does not change the active tour position.
- Previous and Next stop the current audio, move through the existing tour
  navigation model, and begin the selected unit when playback remains active.
- Direct scene, file, or search-result navigation stops the current audio and
  leaves narration paused at the new location. This avoids surprising speech
  when the reader temporarily explores away from the tour.
- Closing the window, loading another tour, losing the selected device voice,
  or encountering an audio error cancels playback and releases resources.
- In standalone, only one Bygone window may own audible narration at a time.
  Starting in a second window pauses the first rather than mixing tours. A
  browser presentation owns only its tab's playback and follows browser media
  controls rather than claiming cross-origin arbitration.

## Quality and engine decision

Device TTS is the always-available default on supported hosts and the normal
offline path. Run a short bakeoff to select the best default device voice and
rate behavior on each supported platform. Evaluate at least:

- the voices available through Chromium/Web Speech on supported platforms;
- enhanced operating-system voices that Electron can invoke without bundling
  a service credential; and
- optionally, one high-quality streamed TTS service as an explicitly enabled
  enhancement configured with the reader's own credential.

Use representative Bygone prose containing file names, initialisms, Git terms,
symbols, and 5–10 minutes of continuous narration. Score naturalness,
technical-word pronunciation, first-audio latency, pause/resume fidelity,
segment completion fidelity, offline behavior, install burden, privacy, and
cost.

The decision gate selects the device integration and default voice per
supported platform; it does not decide whether offline narration exists. If
the readily exposed Chromium voice is poor, use the platform's enhanced local
voice integration in standalone while retaining the best device voice exposed
to `bygone present`. A hosted voice may improve quality when explicitly
enabled, but it never replaces, blocks, or silently activates over the device
default.

Introduce a remote adapter only after device narration ships and evidence
shows that the quality improvement justifies its privacy, credential, and cost
surface. Do not build a speculative provider marketplace.

## Architecture

### Shared narration model

Add a small shared module that converts a validated `ChangeTourManifest` and a
tour position into ordered `NarrationUnit` and sentence-sized
`NarrationSegment` values. Each unit should include:

- a stable ID derived from the scene and optional step IDs;
- normalized plain text;
- the tour position to reveal before playback;
- its role: scene introduction, step, or takeaway; and
- enough ordinal information for accessible status copy.

Each segment adds a stable segment ID, its speech-only normalized text, and a
reference to the exact visible narrative element/range to highlight. Sentence
splitting and normalization must be deterministic and must not mutate the
manifest or the rendered source string.

Keep this model independent of Web Audio, Electron, and any vendor SDK so it
can be tested as pure tour behavior. No `.bygone` source or compiled-manifest
schema change is needed: all required prose and identities already exist.

### Playback controller

The presenter owns a single explicit state machine:

```text
idle -> loading -> playing <-> paused -> completed
                  |       |             |
                  +-------+----> error <-+
```

Commands carry a monotonically increasing request ID. Late synthesis results,
audio events, and completion callbacks from an older request are ignored.
This prevents rapid scene changes or double-clicks from advancing the wrong
tour position.

The controller depends on a narrow speech engine contract: load one narration
segment, play, pause, resume, cancel, report supported device voices/rates, and
emit completion/error events. The controller, rather than engine timing
callbacks, advances the segment highlight and then the tour position.

### Host ownership

Device speech requires no credential. Use the narrowest available local path:

- In the browser presenter, use the device voices exposed by the browser's
  speech-synthesis API and send one known narration segment at a time.
- In standalone, use the same path when it provides the selected device voice,
  or a narrow main-process bridge to an enhanced local OS voice when the
  platform bakeoff justifies it.

Secrets and network calls for an optional hosted enhancement belong to the
trusted host, never to `web/host.js` or the sandboxed tour page.

- In standalone, the main process owns configured remote credentials and the
  cross-window audio lease.
- In `bygone present`, the local presentation server may expose bounded
  same-origin remote-narration endpoints. The client requests a known
  narration-segment ID; it does not submit arbitrary text for the server to
  synthesize.
- The browser presenter receives audio bytes or a short-lived same-origin URL,
  only for an explicitly enabled hosted voice, never the provider credential.

Requests must be size-bounded, cancellable, and restricted to the manifest
already loaded by that server. If a remote engine is selected, disclose before
first use that authored narration text will leave the machine. Never send
source snapshots, diffs, paths not included in the spoken unit, or repository
credentials. Keep generated audio in memory or a session-scoped cache by
default and remove it when the presentation server closes.

### Preferences

Persist device voice, rate, and optional remote-provider consent locally by
host and engine.
Do not write personal playback settings or credentials into `.bygone` files.
Clamp rate to the engine's verified intelligible range and fall back cleanly
when a previously selected voice disappears.

## Delivery slices

### 1. Quality spike and narration contract

- Record the device-engine bakeoff and select the default voice/integration
  for each supported host.
- Implement and test semantic narration-unit extraction, sentence-sized
  segmentation, visible-range mapping, and speech-only normalization for every
  scene kind.
- Settle pronunciation normalization only for demonstrated technical terms;
  avoid an open-ended phoneme or SSML authoring format.

### 2. One-unit playback

- Add Listen, Pause/Resume, cancellation, rate, status, and error behavior for
  the active scene or step.
- Integrate device TTS as the default through the trusted host boundary.
- Highlight the active sentence-sized segment without moving keyboard focus or
  duplicating screen-reader announcements.
- Verify keyboard and screen-reader operation before continuous playback.

### 3. Synchronized full-tour playback

- Advance through the existing linear navigation model on completion.
- Add previous/next behavior, cross-window arbitration, and lifecycle cleanup.
- Preserve the current file/focus synchronization and Return to Tour behavior.

### 4. Hardening and release documentation

- Test long tours, rapid navigation, provider delay/failure, offline changes,
  sleep/wake, window closure, and multiple presentation windows.
- Document the device voice as the default plus any data sent off-device,
  credential setup, and reader-owned costs for an optional hosted voice.
- Exercise both authored and automatically generated tours in standalone and
  `bygone present`.

## Acceptance criteria

- A reader can start, pause, resume, stop, and navigate narration without a
  mouse and can identify the state without hearing it.
- Narration works offline by default on supported hosts through device TTS;
  losing network access does not disable Listen or interrupt device playback.
- Exactly one visible sentence-sized segment is highlighted while spoken, and
  pause retains that position while stop, navigation, error, and completion
  clear it predictably.
- Continuous playback keeps the visible scene, step, file, and focus aligned
  with the spoken unit.
- Every current scene kind produces deterministic narration with no duplicated
  scene introduction during ordinary forward playback.
- Rapid navigation, tour replacement, provider failure, and window closure
  cannot produce stale audio or unintended advancement.
- The chosen device default meets the recorded sustained technical-narration
  quality bar for its supported host; optional remote voices never replace the
  offline default.
- No service secret reaches renderer JavaScript, the tour manifest, logs, or a
  portable artifact.
- Remote synthesis sends only the disclosed narration text and is never
  activated silently.
- Existing tours compile and present unchanged; TTS requires no version-1
  source or manifest migration.

## Scope and non-goals

Included:

- reading tour narrative aloud;
- sentence-sized highlighting synchronized with device speech;
- synchronized scene/step advancement;
- accessible playback controls and local preferences;
- a device engine for each supported environment and an optional hosted
  enhancement only after the local experience ships; and
- explicit privacy, credential, cost, and failure behavior.

Not included:

- microphone access or speech to text;
- questions, chat, explanation generation, or routing to an agent;
- reading arbitrary source code, selections, comments, or search results;
- word-by-word highlighting or highlighting code tokens;
- audio tracks embedded in authored or compiled tour artifacts;
- voice cloning or author-supplied voice models;
- automatic background playback at launch; or
- redesigning the tour narrative schema for speech markup.

## Future direction: opt-in technical-content reading

Treat code and raw-URL exclusion as a first-release default, not a permanent
product rule. After narrative playback is stable, evaluate explicit reader-
invoked actions such as **Read Selection**, **Read Current Change**, and **Read
Link Destination**.

This follow-up needs a different speech contract from prose narration:

- offer concise and verbatim modes for code, because identifiers,
  indentation, punctuation, and deleted/added state carry meaning but become
  exhausting when every symbol is spoken;
- keep code highlighting aligned to the selected line or logical token group
  rather than reusing sentence highlighting;
- speak a link's label by default, with an explicit action to hear a humanized
  destination such as domain and path;
- provide character-by-character URL reading only on request, for cases where
  exact transcription matters; and
- never fetch, resolve, or open a link merely to narrate its destination.

Decide the initial technical-reading surface from accessibility research and
observed demand. Do not add code/URL speech markup to the tour format until the
interaction and pronunciation rules work on content Bygone already renders.

## Risks and decisions

- **Device quality variance:** local browser voices vary materially by OS and
  installed voice packs. Device narration remains the default; the bakeoff
  selects and documents the best supported local path rather than making
  narration network-dependent.
- **Privacy and cost:** excellent hosted speech may require sending narration
  text off-device and using a paid credential. Consent and failure copy must
  be part of the feature rather than setup footnotes.
- **Technical pronunciation:** broad text rewriting can distort authored
  meaning. Normalize only verified cases and retain the original visible text.
- **Navigation races:** synthesis and audio completion are asynchronous. A
  request-generation guard and one playback owner are required.
- **Accessibility regression:** narration complements screen-reader semantics;
  it must not steal focus, suppress live-region updates, or override the user's
  assistive technology.
